# Скилл · Шаг 0 — приём контекста (роль: организатор)

## Задача
Собрать пакет контекста для генерации проектных задач: заявка организатора + четыре основы (паспорт АП, рамка приоритетов, реестр запросов индустриальных партнёров, НТЗ вуза). Проверить достаточность, недостающее добрать глубоким поиском.

## Вход
- Паспорт АП — обязательный документ, его не может не быть. Если не загружен — запроси и жди.
- Предъявленные основы (любые могут отсутствовать): рамка приоритетов, реестр запросов партнёров, НТЗ вуза.
- Требуемое число проектных задач. По умолчанию — число команд АП + 15% (округлить вверх); организатор может указать другое.

## Вход заказчика vs материалы агента (важно — правило разграничения)

**Вход Шага 0 — только документы, предъявленные заказчиком как вход** (минимум — паспорт АП). Всё прочее в рабочем окружении (справки прошлых исследований, перечни запросов сторонних компаний, файлы «для примера», архивы прошлых волн) — **не вход заказчика**, даже если они лежат рядом с загруженными документами:

- Файл «для примера/референса» (например, чужой перечень задач индустриального партнёра, по которому проектировался шаблон) — справочник формата, а не источник запросов: задачи от его содержимого не генерируются, его владелец не назначается покупателем.
- Неуверен в статусе документа (вход, референс, фон) — спроси организатора до начала добора; если спросить не у кого — считай референсом и пометь это в протоколе (07).
- Основы, сгенерированные агентом (рамка, реестр, НТЗ), в workspace помечай «сгенерировано агентом на Шаге 0» — организатор должен видеть, что предъявлено им, а что собрано агентом.
- Дублирует правило источников в `instructions/deep-research.md`: опора задач — только подтверждённые входы заказчика и открытые источники, найденные самим агентом.

## Процедура
1. **Большие документы читай частями** (паспорт АП часто 100+ тыс. токенов — цельное чтение переполняет контекст и ломает Шаг 1): сначала оглавление и структура (фактическим поиском), затем целевые разделы — «Основная часть» (направление, сегменты, сроки, сквозные технологии), приложения с партнёрами и задачами; таблицы выписывай сразу при чтении раздела. Полное чтение файла запрещено, если он больше ~30–40 тыс. токенов; ошибка API «maximum context length» — сигнал вернуться к частям, а не повторять запрос.
2. **Сырьевой пул Шага 1 — обязательная таблица задач: ищи в паспорте по названию/контексту, не по номеру** (нумерация таблиц в разных паспортах АП различается). Кандидаты по содержанию: «Задачи индустриальных партнеров» (перечень задач партнёра с описанием — главный сырьевой пул), «Задачи от научных подразделений / лабораторий / передовых инженерных школ вуза», «задачи партнёров и задачи научных подразделений» в любом формулировании. Извлеки такую таблицу(ы) ПОЛНОСТЬЮ: каждая задача — с ID/номером, партнёром-держателем и текстом; это основа реестра партнёров (05) и главный источник задач Шага 1. Если таблицы нет — так и зафиксируй в протоколе (07): сырьевой пул пуст, задачи Шага 1 строятся только от рамки и НТЗ.
3. Извлеки параметры заявки из паспорта АП и заполни `templates/03-organizer-request.md`. Всё, чего в паспорте нет, — пометь и запроси у организатора. Кастомизация параметров — только по его явному указанию. Перед извлечением просканируй структуру паспорта фактическим поиском (не по оглавлению) и перечисли в протоколе (07) все его разделы, таблицы и приложения со статусом «найдено/отсутствует в тексте» — ✅ ставится только после проверки. Паспорт читай до конца, включая таблицы: именно в них — задачи индустриальных партнёров и задачи научных подразделений (сырьевой пул Шага 1).
4. Принятые основы разложи по шаблонам: рамка приоритетов — `templates/04-priorities-frame.md`, реестр партнёров — `templates/05-partner-requests-registry.md`, НТЗ — `templates/06-university-research-base.md`. Папка `workspace/0-context/`.
5. Если реестр партнёров предъявлен без структурированных запросов (или не предъявлен вовсе, а перечень партнёров есть) — веер по партнёрам **исполняется в рамках Шага 0, а не откладывается**: для каждого партнёра — его сайт (продукты, специализация, инновационные программы), публичные запросы на инновации, закупки НИОКР, индустриальные новости. Результат — заполненный реестр с источником по каждому пункту. Это главный поставщик сырьевого пула для Шага 1; без него генерация теряет опору «запросы партнёров».
6. Прогони `templates/07-context-sufficiency-checklist.md` блок за блоком; результат — протокол проверки достаточности: что предъявлено и полно, что предъявлено с пробелами, чего нет.
7. Пробелы закрой глубоким поиском по `instructions/deep-research.md` — ПРОЧИТАЙ ЕГО ЦЕЛИКОМ ДО ПЕРВОГО ПОИСКОВОГО ВЫЗОВА (в инструкции задан приоритет каналов: основной — Yandex Search API; другие поисковики/MCP произвольно не подменять): основной поисковый механизм — Yandex Search API по рецепту `instructions/yandex-search-recept.py` (ключ организатора в окружении; проверочный вызов ключа перед сбором; бюджет квотами по каналам; веер запросов, иерархия источников, правило двух опор, проверка статус/дата/редакция каждого источника, проверка стартовых подсказок задания). Если ключ не задан/не работает или поиск нестабилен (зависания, заглушки, обрывы) — не блокируй шаг: переходи в резервный режим инструкции (веер запросов и план ручного сбора организатору), сохрани найденное и веер запросов приложением к недостроенной основе (например `04a-рамка-глубокий поиск.md`), недобранное честно пометь пробелом и продолжай; добор — повторным глубоким поиском или вручную организатором.
8. Рамка приоритетов: в паспорте АП обычно есть только рынки НТИ и сквозные технологии — явно пометь «это сырьё рамки, не рамка приоритетов», дострой карту приоритетов по направлению и покажи организатору разрыв: «было в паспорте → добавлено из источников».
9. Всё найденное поиском отдай на подтверждение организатора до использования на следующих шагах.
10. Покажи итоговый состав `workspace/0-context/` с статусом каждой из 4 основ: предъявлена организатором / сгенерирована агентом / не собрана — и что добрано поиском. Переход к Шагу 1 — ТОЛЬКО после явного подтверждения организатора «переходим»; при несобранной рамке приоритетов (04 остаётся сырьём/планом добора при доступном поиске) генерацию не начинай: покажи разрыв и предложи добор (основной механизм — Yandex Search API) или резервный режим. Пропуск добора допустим только при недоступном поиске и по явному решению организатора.

## Границы
- Не фантазируй приоритеты, данные вуза и партнёров; каждое утверждение — с источником.
- Не требуй чувствительных сведений; состав загружаемых данных определяет организатор.
- Не генерируй задачи на этом шаге.
