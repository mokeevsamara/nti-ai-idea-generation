# ИИ-ассистируемая генерация идей в рамках акселерационных программ

**Методическое описание процесса**

Версия 1.0, 15.10.2026. Обновления по итогам альфа-тестирования пакета агента; опубликована в репозитории проекта (github.com/mokeevsamara/nti-ai-idea-generation).

## 1. Назначение

Настоящий документ описывает методику организации этапа генерации идей в акселерационной программе (АП) вуза с поддержкой ИИ-ассистентов. Методика универсальна и применима любым вузом-организатором АП: вся специфика вуза вводится как входные параметры и документы (раздел 4), ничего не зашивается в саму методику.

Методика решает две задачи:

- сделать генерацию идей системной и управляемой: проектные задачи рождаются на пересечении государственных приоритетов технологического развития, компетенций и инфраструктуры вуза, запросов индустриальных партнёров и содержательных рамок конкретной АП — а не в режиме неуправляемого мозгового штурма;
- провести команду участника от выбранной задачи к первичному проектному описанию, с которым команда приходит к трекеру/экспертам уже с минимальной проработкой, а не с сырой идеей.

ИИ-ассистенты в настоящем документе описаны как «чёрный ящик»: зафиксировано, что ассистент делает на каждом шаге, что получает на входе и что отдаёт на выходе. Техническая реализация и алгоритмические параметры ассистентов — предмет отдельных документов.

## 2. Роли и границы ответственности

| Роль | Что делает |
|---|---|
| Заказчик (оргкоманда АП) | Подаёт заявку на генерацию проектных задач и документы (Шаг 0); валидирует сгенерированные задачи; организует выбор задач командами; сопровождает процесс |
| Команда участников | Выбирает проектную задачу; формирует первичное проектное описание с поддержкой ассистента |
| ИИ-ассистент | Генерация задач, проверка соответствия рамке, фасилитация упаковки, аналитическая критика; действует только в рамках настоящего процесса |
| Трекеры, наставники, эксперты | Получают команду с пакетом материалов и ведут её по программе акселератора (вне настоящего процесса) |

Базовые принципы:

- Ассистент помогает и фасилитирует, но не делает работу за людей: содержание задач и проектов формулируют заказчик и команда.
- Все вердикты ассистента носят рекомендательный характер; решение всегда остаётся за людьми.
- Акселератор — часть обучения студентов: задача без образовательной ценности не допускается в перечень независимо от прочих достоинств.

## 3. Карта процесса

**Шаг 0** (подготовка контекста) → **Шаг 1** (генерация базы проектных задач) → валидация задач заказчиком → **выбор задачи командой** (ярмарка проектных идей) → **Шаг 2** (от задачи к первичному проектному описанию) → передача в акселератор (трекер/эксперты).

| Этап | Кто действует | Вход | Выход |
|---|---|---|---|
| Шаг 0 | Заказчик + ИИ-ассистент | Материалы заказчика, открытые источники | Пакет контекста |
| Шаг 1 | ИИ-ассистент (+ заказчик) | Пакет контекста, параметры заказчика | Перечень проектных задач |
| Валидация задач | Заказчик | Перечень задач | Утверждённый перечень |
| Выбор задачи | Команды (+ опции ассистента) | Перечень задач | Выбранная задача / идея / проект команды |
| Шаг 2 | Команда + ИИ-ассистент | Выбранная задача, форма паспорта проекта АП | Первичное проектное описание + пакет для трекера |
| Акселератор | Трекеры, наставники, эксперты | Пакет для трекера | — (обычный контур АП) |

## 4. Шаг 0 — подготовка контекста

Цель шага — создать основы для работы по генерации идей.

### 4.1. Заявка организатора на генерацию проектных задач

Заявка на генерацию проектных задач формируется из паспорта АП; организатор проверяет извлечённые параметры и дополняет недостающее (артефакт Шага 0):

- технологическое направление АП;
- длительность акселерации;
- число команд/участников;
- требуемое число проектных задач;
- критерии образовательного потенциала (принимаются из паспорта АП);
- опционально: итоги прошлых волн — проекты, «выстрелившие» по итогам прошедших акселераторов. Прошлые волны могли идти по другим направлениям, поэтому их итоги используются только как косвенная рамка с низким весом.

### 4.2. Четыре основы

1. **Рамка государственных приоритетов** по технологическому направлению АП — карта того, что важно государству и индустрии в данном направлении (технологический суверенитет и технологическое лидерство). Рамка собирается как каскад от нормативной базы к точкам приложения задач: действующие национальные проекты технологического лидерства (НПТЛ) и их паспорта, критические и сквозные технологии, отраслевые задачи и приоритеты, ландшафт уже существующих решений, индустриальные подтверждения (открытые запросы и закупки) — итогом служит карта технологических барьеров и точек роста направления, из которой рождаются задачи Шага 1. Если заказчик рамку предъявляет — она проходит проверку полноты; если не предъявляет — собирается ИИ-ассистентом глубоким исследованием открытых источников. Типовой случай: в паспорте АП есть только рынки НТИ и сквозные технологии — это сырьё рамки, а не рамка; недостающее достраивается исследованием, и заказчику явно показывается разрыв: «было в паспорте → добавлено из источников».
2. **Паспорт акселерационной программы** — готовый документ заказчика с методологией акселерации; используется как есть.
3. **Запросы/задачи индустриальных партнёров** (может отсутствовать). Если отсутствует или неполно — глубокое исследование открытых данных о партнёрах акселератора: чем занимаются, доступная информация о технологиях и проектах — всё, что может помочь в формировании базы задач.
4. **Научно-технический задел вуза** (может отсутствовать). Если отсутствует или неполно — глубокое исследование открытых источников: кафедры, лаборатории, публикации, флагманские проекты, направления исследований, инфраструктура.

### 4.3. Правила работы с данными

- Всё, что заказчик предъявил, проверяется на достаточность и при необходимости дополняется исследованием; всё, что не предъявлено, исследуется по умолчанию.
- Результаты исследования приводятся с указанием источников и подтверждаются заказчиком до использования на следующих шагах: заказчик знает свой вуз и партнёров лучше автоматического поиска.
- Вход Шага 0 — только документы, предъявленные заказчиком как вход (минимум — паспорт АП). Прочие материалы рабочего окружения (справки прошлых исследований, перечни задач сторонних компаний, файлы «для примера», архивы прошлых волн) входом не считаются, даже если лежат рядом с загруженными документами: файл-референс — справочник формата, его содержимое не источник задач и его владелец не покупатель. Статус спорного документа выясняется у организатора до начала добора; если спросить не у кого — материал считается референсом и помечается.
- Основы, собранные ассистентом (рамка, реестр партнёров, НТЗ), помечаются «сгенерировано агентом на Шаге 0»: заказчик всегда видит, что предъявлено им, а что собрано ассистентом.
- Заказчик сам определяет состав передаваемых ассистенту данных.

### 4.4. Поисковый слой

Глубокое исследование выполняется ассистентом с доступом к поисковому сервису, ключ которого получает организатор вуза (собственный ключ организатора, а не встроенный поиск агентной среды: сбор российского нормативного слоя через встроенные каналы даёт незаметные пробелы). Перед сбором ассистент делает проверочный вызов ключа; если ключ не выдан или недоступен — резервный режим: ассистент формирует перечень запросов и план сбора, источники собирает организатор вручную. Сбор ведётся по эшелонам источников — от нормативной базы и программных документов до отраслевой статистики и открытых индустриальных запросов; каждый источник проверяется на статус, дату и редакцию; реквизиты из задания («стартовые подсказки») проходят ту же проверку, что и найденное.

### 4.5. Выход шага

Пакет контекста: заявка организатора + четыре основы + протокол проверки достаточности (что предъявлено полно, что с пробелами, что собрано ассистентом и подтвердилось). Фиксируется как артефакт, используется на всех последующих шагах и сохраняется заказчиком для переиспользования в следующих волнах.

## 5. Шаг 1 — генерация базы проектных задач

### 5.1. Что генерируется

Перечень проектных задач, которые могут быть предъявлены участникам АП для разработки студенческих проектов. Каждая задача рождается в рамке четырёх основ: государственный приоритет + задачи индустриальных партнёров + задел вуза + содержательные рамки АП.

Тематическая специализация задаётся паспортом АП (перечень направлений и сегментов рынка) и расширению ассистентом не подлежит: глубокое исследование дополняет рамку приоритетов, но не перечень сегментов заказчика. Сквозные технологии (например «ИИ в отраслях») — признак способа решения, а не сегмент: одного их соответствия недостаточно, чтобы отнести задачу к специализации АП.

### 5.2. Паспорт проектной задачи (референсный состав полей, настраивается заказчиком)

- название проектной задачи — короткая формулировка без готового решения;
- проблема и технологический барьер — что решаем и какое ограничение снимаем;
- технологический объект — материал, компонент, данные, модель, оборудование, процесс, метод контроля: что создаётся или меняется;
- направление — в рамках какого технологического направления АП решается;
- связь с приоритетом — НПТЛ / приоритетные направления НТР / важнейшие технологии;
- подтверждение — официальный источник и индустриальное подтверждение (для задачи от партнёра — сам партнёр);
- потенциальный потребитель — конкретный партнёр либо профиль рыночного потребителя;
- пользователь и площадка проверки — кто применит решение, где проверяется гипотеза;
- минимальный контур на срок акселерации — что нужно решить за акселератор;
- ожидаемый результат и критерий успеха — что будет создано и как измерено;
- потенциальный РИД — охраняемый результат интеллектуальной деятельности;
- направления подготовки студентов — какие направления подготовки вуза закрывают команду;
- минимальная ролевая модель команды.

### 5.3. Рамочные критерии

Каждая задача должна:

1. лежать в поле государственных приоритетов;
2. лежать в поле технологических компетенций вуза;
3. быть потенциально реализуемой в рамках акселератора: за срок акселерации силами студенческой команды с инфраструктурой вуза достижимо измеримое приращение готовности (минимум +1 уровень готовности TRL/MRL). Для deep-tech задач, которым работоспособный прототип за срок акселерации недостижим, требуется достижимый промежуточный результат (например, переход от кабинетного анализа к экспериментальной проработке). Задачи, сводящиеся к типовой инженерной рутине без технологического содержания, не допускаются;
4. иметь рыночный потенциал / потенциал коммерциализации и не быть привязанной к единственному заказчику: индустриальный партнёр — первый покупатель/пилотный пользователь, но решение должно быть обобщаемо на сегмент рынка (проверяется именно обобщаемость). Партнёр называется первым покупателем только если задача происходит из его запроса (реестр запросов или таблица задач паспорта АП); иначе партнёр указывается как «кандидат в покупатели» — приписывать партнёру несделанный заказ нельзя. Задача, порождённая заделом вуза без партнёра-заказчика: потребителя не фабрикуется, критерий получает статус «условно», судьбу задачи решает организатор при валидации;
5. иметь образовательный потенциал: команда должна учиться на этой задаче основам технологического предпринимательства согласно рамкам паспорта АП.

### 5.4. Контроль качества

Генерация обязательно включает цикл ИИ-ассистируемой проверки каждой задачи на соответствие рамочным критериям (п. 5.3) с перегенерацией несоответствующих задач. Проверка включает раздельный вердикт по каждому из пяти критериев с обоснованием и ссылкой на конкретное место пакета контекста; вердикты сохраняются в паспорте задачи. Задачи, у которых сильные значения по одним критериям сочетаются с провальными по другим (например, высокая актуальность по приоритетам при нулевой образовательной ценности), отсекаются.

### 5.5. Валидация заказчиком

После ИИ-ассистируемой валидации перечень проходит методический шаг валидации заказчиком. Как именно заказчик валидирует (сам, с экспертами, с индустриальными партнёрами, с другим ИИ или без отдельной валидации) — на усмотрение заказчика; в контур ассистента этот шаг не входит.

### 5.6. Число задач

Требуемое число проектных задач задаёт заказчик исходя из числа участников и имеющегося (если есть) перечня задач. Если не задано — по умолчанию число команд АП + 15% (запас на отсев при валидации).

**Выход шага** — перечень проектных задач в требуемом объёме, соответствующий рамочным критериям.

## 6. Выбор задачи командой (ярмарка проектных идей)

Организационное мероприятие заказчика (например, «ярмарка проектных идей»). Выбор задачи команда делает сама; ИИ в контуре выбора не задействован.

Опциональные модули поддержки (включаются по решению заказчика):

- **Досье задачи** — ассистент-чат, в котором команда может дополнительно «допрашивать» задачу перед выбором: что имеется в виду, что уже есть в вузе, кто партнёр. Снижает барьер незнакомства команд с технологическими направлениями.
- **Матчинг «команда ↔ задача»** — команда по желанию заполняет короткую анкету (состав, компетенции, интересы), ассистент ранжирует задачи базы с объяснением соответствия. Опционально — по желанию организаторов и команд.
- **Валидация собственной идеи или проекта команды.** Команда может прийти не с задачей из перечня, а со своей идеей («мы вот что придумали») или уже существующим проектом («у нас есть вот такой проект») любой степени готовности. Механизм проверки тот же, что в п. 5.4, применённый к материалу команды; глубина проверки сообразна степени готовности и глубине описания входа. Вердикт рекомендательный: низкая валидность по ключевым критериям — не блокер, а пространство для решения организатора и команды.

## 7. Шаг 2 — от задачи к первичному проектному описанию

Цель шага — помочь команде превратить выбранную задачу (или собственную идею/проект) в первичное проектное описание, минимально необходимое и достаточное для входа в акселератор.

### 7.1. Первичная упаковка

Основа — форма «паспорт проекта», общая для всех АП (у вуза своей формы нет); из неё берётся минимально необходимый объём полей описания проекта (полная форма заполняется позже, в контуре акселератора). Индивидуальная форма — только если заказчик её явно задаёт. Команда выбирает режим:

- самостоятельное заполнение первичного паспорта с передачей ассистенту;
- ИИ-ассистируемое заполнение в режиме фасилитационной поддержки: ассистент работает вопросами по блокам полей, помогает сформулировать содержание на языке команды, каждое положение подтверждается командой. Ассистент не сочиняет за команду — он помогает как наставник.

### 7.2. Технооптимист

Ассистент в роли технооптимиста готовит по первичному паспорту аналитический отчёт: что в проекте сильного, какие есть удачные решения, какие неочевидные возможности (инсайты) и нестандартные ходы команда могла не увидеть.

### 7.3. Технопессимист

Ассистент в роли технопессимиста готовит аналитический отчёт: слабые стороны, ограничения, узкие места, что может пойти не так.

### 7.4. Переупаковка

По итогам отчётов технооптимиста и технопессимиста ассистент (в режиме фасилитации) помогает сформировать список рекомендуемых улучшений первичного проектного описания.

### 7.5. Решение команды

По итогам цикла команда решает:

- принять корректировки и повторить процедуру первичной упаковки;
- принять корректировки и завершить упаковку;
- не принимать корректировки и идти дальше.

### 7.6. Пакет для трекера

Итог шага — первичное проектное описание (первичный паспорт проекта) и пакет материалов для трекера/эксперта:

- проектное описание;
- краткое резюме «что изменено после критики и почему»;
- отчёты технооптимиста и технопессимиста (приложения).

Пакет показывает трекеру зрелость команды и историю её решений и экономит время нулевого цикла.

## 8. Передача в акселератор

С этого момента команда работает с людьми — трекером, наставниками, экспертами — в обычном контуре акселерационной программы. Контур ИИ-ассистентов завершён.

## 9. Настраиваемые места (адаптация под заказчика)

- Референсный состав полей паспорта проектной задачи (п. 5.2).
- Минимально необходимый набор полей первичного паспорта — из общей формы паспорта проекта; индивидуальная форма — только по явному указанию заказчика.
- Критерии образовательного потенциала — из паспорта АП.
- Состав опциональных модулей этапа выбора (раздел 6).
- Состав и глубина основ Шага 0 (пп. 4.2–4.4).

## 10. Глоссарий

- **АП** — акселерационная программа.
- **Проектная задача** — задача для разработки студенческого проекта в ходе АП, порождаемая в рамке четырёх основ (Шаг 1).
- **Паспорт проектной задачи** — описание задачи по референсному набору полей (п. 5.2).
- **Первичное проектное описание (первичный паспорт проекта)** — минимально необходимое и достаточное описание проекта команды, итог Шага 2.
- **Заявка организатора на генерацию проектных задач** — набор параметров запуска, формируемый из паспорта АП и уточняемый организатором (п. 4.1).
- **Глубокое исследование** — систематический сбор и обобщение открытых источников ассистентом с указанием источников.
- **Пакет контекста** — артефакт Шага 0: заявка организатора + четыре основы.
- **Пакет для трекера** — артефакт передачи команды в акселератор (п. 7.6).
- **TRL / MRL** — уровни готовности технологии / производства.
- **НПТЛ** — национальные проекты технологического лидерства (с 2025 г. — девять действующих проектов).
- **Рамка приоритетов** — основа Шага 0: каскад от нормативной базы до карты технологических барьеров и точек роста направления (п. 4.2).
- **Сырьё рамки** — фрагментарные сведения о приоритетах в паспорте АП (обычно рынки НТИ и сквозные технологии), требующие достройки до полной рамки (п. 4.2).
- **Первый покупатель / кандидат в покупатели** — индустриальный партнёр, чей запрос породил задачу / партнёр, чья заинтересованность не подтверждена его запросом (п. 5.3).
